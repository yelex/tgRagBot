## Найденные проблемы

### P1 — N10_delivery пропускается, данные не сохраняются (критично)

**Симптом:** После того как пользователь вводит дату+время в одном сообщении
(«Завтра в 12:00»), routing LLM решает «всё собрано → payment»
и прыгает в N13_photo минуя `_N10_delivery_node`.
В итоге: собранные данные (дата, время, адрес) не оседают в `collected_data`
(нода не вызывалась), поле `recipient_phone` не спрашивается,
в сводке нет номера заказа.

**Корень проблемы:** routing LLM принимает решение о переходе на основе
истории чата (что было написано), а не содержимого `collected_data`.
Он видит «адрес был раньше, сейчас дата+время» → думает «данные есть» →
переходит в payment. Но `_N10_delivery_node` никогда не вызывался
для финальной сохранения и проверки.

**Возможные решения:**
- A) Передавать `collected_summary` с явным указанием что уже собрано в `collected_data`
  (а не просто из истории). Тогда LLM будет видеть «delivery_time: нет» и оставаться в N10.
- B) Изменить логику: переход payment → только если `_N10_delivery_node`
  сам выставил phase=payment после проверки всех полей.
  То есть routing LLM не должен прыгать в payment напрямую из N10_delivery —
  только через N10_delivery node.
- C) В `_N10_delivery_node` в начале всегда извлекать сущности из последнего
  сообщения, даже если routing уже решил перейти дальше (т.е. phase уже payment).

**Рекомендуется вариант B:** добавить в routing prompt: «payment НЕ является
прямым переходом из N10_delivery — только сам N10_delivery node решает,
когда данных достаточно».

### P2 — `bouquet_name` не сохраняется при выборе по имени (средне)

**Симптом:** Пользователь пишет «Букет Модена» в фазе N9_offer.
Routing LLM корректно ставит next_phase=N10_delivery + name_query=«Модена».
Но Б2-фикс в `_N10_delivery_node` ищет по `name_query` в `_last_bouquets[user_id]`,
а там может не быть букета с «Модена» в названии или `_last_bouquets` пуст
для данного `user_id` (тест использует других user_id чем живой бот).

**Решение:** В N10_delivery искать не только в `_last_bouquets` но и во всём
`state["bouquets_data"]` по fuzzy match, если точного нет в кэше.

---

### P3 — Бюджет ниже минимума не перехватывается в N9_offer (среднее)

**Симптом:** «Букет за 2000» → routing LLM прыгает в N9_offer с budget_max≈2000.
N2_brief с проверкой минимума не вызывается.
Бот показывает варианты (дешёвые из каталога с ценой 0) вместо
«минимальный заказ 5 000 ₽».

**Решение:** В начале `_N9_offer_node` добавить проверку budget_max < 5000 →
показать сообщение о минимуме и вернуть в N2_brief_budget.

---

### P4 — Routing LLM иногда путает FAQ с брифом (мягкое)

**Симптом:** «Сколько стоит доставка за МКАД?» → routing ставит N2_brief_budget
(бот отвечает на вопрос о доставке но в контексте брифа).
Ответ содержит правильную информацию («1 000 ₽ + 50 ₽/км от МКАД»),
но phase неправильная и дальше бот спрашивает бюджет.

**Решение:** Либо усилить примеры в routing prompt для FAQ,
либо принять что ответ пользователю правильный — просто phase в тесте
ожидается не та (смягчить проверку).

## Что было сделано в этой итерации

1. **Б1 — N9_offer сохраняет бюджет** — `entities["max_price"]` теперь персистируется
   в `collected["budget_max"]` при входе в N9_offer.
   Также сохраняются `occasion`, `recipient`, `product_type`, `gamma`.

2. **Б2 — N10_delivery ищет букет по name_query** — если `bouquet_name` пустой,
   пытается найти по `entities["name_query"]` в `_last_bouquets` и каталоге.

3. **Б3 — N3_catalog парсит диапазон «5000-10000»** — regex fallback для формата
   `min-max` без слов «от»/«до».

4. **Б4 — Корпоратив/свадьба → N12_escalation** — добавлено в PRIORITY правила
   routing prompt.

5. **Rate limiting** — retry с exponential backoff (3 попытки, 2/4/8s).
   Sleep между вызовами увеличен с 0.5s до 1.0s.

6. **Routing prompt: N10_delivery держит фазу** — явное правило «оставайся в
   N10_delivery пока адрес+дата+время не собраны».

7. **Тест-раннер** — пауза 3s между сценариями для соблюдения rate limit.
   Улучшена extraction `collected_data` (brace-counting вместо regex).
   Улучшена extraction цен (только явные цены букетов, не заголовки категорий).

## Следующие шаги (приоритет)

### 1. Исправить P1 (routing обходит N10_delivery)

Добавить в routing prompt:

```
ВАЖНО: переход в payment возможен ТОЛЬКО из N10_delivery node,
не напрямую. Если текущая фаза N10_delivery и данные выглядят
полными — всё равно оставайся в N10_delivery; нода сама решит
когда переходить.
```

Это самый важный фикс — закрывает сразу сценарии 1, 8, 9, 15.

### 2. Исправить P3 (бюджет < 5000)

В начале `_N9_offer_node`:
```python
budget = collected.get("budget_max") or entities.get("max_price") or 0
if budget and budget < 5000:
    state["response"] = "Минимальный заказ — 5 000 ₽. Рассматриваете?"
    state["phase"] = "N2_brief_budget"
    return self._wrap_response(state)
```

### 3. Исправить P2 (bouquet_name по имени)

В Б2-коде в N10_delivery: расширить поиск на весь `state["bouquets_data"]`
с частичным совпадением (fuzzy, не exact).

### 4. Смягчить или убрать P4 из тестов

FAQ в контексте «только что был бриф» → routing LLM путается.
Либо улучшать routing prompt, либо тест изменить на проверку
содержимого ответа (есть МКАД и ₽) а не фазы.
